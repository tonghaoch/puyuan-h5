# 濮院游园 H5 技术方案

状态：2026-11-17 的技术设计基线。后续已建立可交互的示意地图版本；当前实现与尚未接入的能力见 [实现记录](implementation.md)。本文中的地理配准与微信 JS-SDK 为后续目标，不代表已经完成。

## 1. 已确认的产品方向

- 独立微信 H5 项目，优先适配微信内的 iPhone 与 Android 手机，也可在普通浏览器查看。
- 默认地图；另外两个 tab 分别是餐厅列表、活动列表。
- 地图上的地点 pin 可打开详情；同一地点可以承载多个活动。
- 只重建古镇游览范围内的建筑、水系、道路、桥梁和设施，排除参考图中的周边住宅与产业区。
- 用户已确认地理准确优先，在真实布局上绘制手绘风格。
- 用户已确认中式复古、古风游戏式华丽 2.5D 建筑与局部动画；固定视角，可拖动缩放。
- 本阶段不做实时 3D 旋转、最终视觉稿或完整产品功能。

## 2. 最重要的技术判断

参考图是带透视、局部比例变化的导览插画，不能通过裁切、两个角点或一次经纬度线性换算，成为准确的定位地图。即使四角对齐，内部街巷仍可能偏移。

采用“真实地理底稿 → 手绘地面 → 预渲染 2.5D 建筑 → 动画与交互层”的制作路线。原图用于辨认风格和候选设施，精确位置另找依据。不能从这张图中读取或猜测精确经纬度。

最终定位的误差包含三部分：地理底稿的误差、绘图配准的误差、手机定位的误差。改善绘图不能消除窄巷、屋檐或室内的卫星定位漂移。

## 3. 推荐技术栈

| 部分 | 初步选择 | 原因 |
| --- | --- | --- |
| H5 | Vue 3 + TypeScript + Vite | 适合移动端交互，工程简单，页面与地图逻辑可分开 |
| 地图 | MapLibre GL JS | 管理投影、镜头、瓦片、地理图层与点击命中；可仅加载自有地图 |
| 地理数据 | 带来源和版本的 GeoJSON | 保存园区范围、河流、道路、桥、建筑轮廓、地点和入口 |
| 美术底图 | 分级栅格瓦片 | 装载当前视野需要的细节，避免一次下载或解码整张超大图 |
| 局部动效 | CSS + 少量 Canvas | 先满足 pin、灯光、水面等效果；复杂动效再评估 PixiJS |
| 微信能力 | JS-SDK + 小型签名后端 | 定位、分享等能力需要正确配置和签名 |
| 初期内容 | 版本化 JSON | 自用阶段可直接维护，未来按需要接 CMS |
| 发布 | HTTPS 静态托管 + CDN + 签名函数 | 前端内容和素材易缓存，公众号凭据只放后端 |

当前示意地图使用独立的 SVG 场景实现交互；MapLibre 在真实地理底稿验证后接入。地图渲染库不提供濮院底图、地点目录或精确坐标，这些需要独立准备。

MapLibre 默认保持 pitch=0、bearing=0，关闭旋转与倾斜手势；建筑立体感来自资产本身。不要把已有透视的画面再次倾斜。若微信实机上的 WebGL 表现不达标，再用同一套地理数据和瓦片评估 Leaflet，无需在第一版同时维护两套引擎。

## 4. 地图制作与坐标流程

### 4.1 先确认真实范围

需要拿到或核实当前园区边界、入口、开放区域和设施名称。参考图可能反映规划状态，不自动等同于今天可游览的范围。游客中心、水上舞台、濮商会馆等只作候选清单，活动和营业情况不从图片推断。

底稿优先级：带坐标说明的官方总平图或 GIS 数据；可配准的 CAD；具有明确坐标与使用条件的底图；现场核验与测点作为补充。CAD 的本地工程坐标不能直接当作经纬度。

### 4.2 固定一套规范坐标

- 自有 GIS 数据优先采用 WGS84 经纬度；GeoJSON 坐标数组统一为 [longitude, latitude]。
- MapLibre 的 Web Mercator 投影负责把地理位置映射到地图平面。EPSG:3857 的投影转换与 WGS84/GCJ-02 的转换是不同问题。
- 微信定位显式请求与地图约定一致的类型，首选 wgs84；浏览器定位按 WGS84 处理。
- 如果后续底稿来自高德等使用 GCJ-02 的体系，先核实数据，再决定统一到哪一套。严禁把 GCJ-02 点直接贴到 WGS84 底图；转换集中处理，不能在各页面重复换算。
- 每份地理资产记录原始坐标体系、转换过程、数据来源、范围与版本。

### 4.3 地面与建筑分开制作

1. 在地理底稿上绘制河岸、街巷、桥梁和建筑的真实地面轮廓。
2. 固定整张地图的观看方向、光照和建筑比例。重点地标单独制作，普通建筑复用屋顶与立面素材。
3. 把模型离线渲染成透明素材，或直接绘制 2.5D 建筑；按真实建筑地面轮廓摆放。
4. 区分建筑的地面锚点与屋顶的视觉偏移。pin 的尖端指向入口或活动区域，不能因为屋顶好看而移动真实坐标。
5. 把静态层合成为带地理参考的分级瓦片；需要动画的水面、灯笼、树影等保留单独图层与地理锚点。
6. 保存建筑轮廓与入口点的 GeoJSON 用于点击命中、筛选和定位，不能只留下绘制好的图片。

### 4.4 配准与验收

如需从无坐标的总平图建立底稿，选取分布均匀的地面控制点，例如桥头、道路交叉点、建筑入口；屋顶尖角不宜作为地面控制点。控制点数量与变换方式由原始素材决定，先以 8–15 个分散点作为试验计划，另外保留独立检查点。

检查点不参与拟合。分别记录各点误差、平均误差与最大误差，重点检查狭窄街巷和河岸。数据质量支持时，可把独立检查点误差不超过 3–5 米作为试验目标；这不是对手机定位精度的承诺。若原图局部畸变严重，应重新绘制对应区域，不能靠越来越复杂的扭曲弥补。

首个样片只选相邻的一座桥、一段河流与一组建筑，先验证坐标、美术、缩放、动效和低端机性能，再扩展全园。

## 5. 用户定位

默认允许不授权位置也能完整浏览地图与列表。用户主动点击定位后再发起授权。

优先使用配置成功的微信 JS-SDK；普通浏览器使用 Geolocation。微信能力不可用时可提供浏览器定位的备用入口；用户拒绝定位后停止请求，不能切换接口反复弹授权。

定位模块返回明确状态：未启用、请求中、可用、精度有限、过期、拒绝、不可用、错误。一次定位结果包含坐标、坐标类型、来源、获取时间和可用的精度信息。微信与浏览器的精度字段按各自文档解释，未提供可靠数值时不虚构精度圆。

- 首次有效定位可移动镜头到用户附近。用户拖动地图后退出自动跟随，再点定位恢复。
- 微信 getLocation 是单次获取；需要更新时由模块控制节奏，不承诺持续后台定位。支持的浏览器可使用 watchPosition，并在离开页面时释放。
- 页面对用户可见时才更新；切到后台暂停，回来后判断结果是否过期。过期阈值与更新间隔通过实机测试确定。
- 校验时间、精度和不合理跳跃，避免画面来回抖动；不把用户强行吸附到可能隔着河的最近道路。
- 使用园区 polygon 判断是否在范围内，并结合精度范围处理“边界附近，无法确定”。园外用户不移动到园区边缘假装在园内。
- 用户位置只在设备中使用；第一版无需账号、轨迹上传或位置数据库。

显示建筑与用户位置正确是第一阶段目标。园内导航需要另外建立可步行路网，标记桥梁、围墙、闸口、开放时段和无障碍路线；不能用两个点之间的直线冒充步行路线。列表如显示距离，必须标明直线距离，且只在有效位置可用时计算。

## 6. 数据与交互模型

| 对象 | 关键内容 | 关系 |
| --- | --- | --- |
| Place 地点 | id、名称、类别、真实位置、入口、建筑轮廓、图片、开放规则、核验状态 | 所有内容的地理锚点 |
| Activity 活动 | id、标题、介绍、图片、状态、预约信息 | 活动内容本身，不与建筑绑定成一个对象 |
| Session 场次 | activityId、placeId、起止时间、取消状态 | 同一活动可多场次，也可更换举办地点 |
| Restaurant 餐厅 | id、placeId、菜系、人均、营业规则、联系电话 | 与地点关联，位置不重复维护 |
| Facility 设施 | placeId、类型、开放情况 | 厕所、出入口、服务点等通过地点表示 |
| MapAsset 地图版本 | 版本、坐标体系、范围、瓦片配置、来源、核验记录 | 保证地图与地点数据相互匹配 |

活动时间统一使用 Asia/Shanghai，并保存明确时区的时间；场次取消、跨日、临时闭店、营业信息未知都必须能表达。未知不能默认写成“营业中”。初期数据文件可手工维护，但运行时仍应验证坐标、引用关系和时间字段。

地图 pin 表示地点，同地点的多场活动合并；点击后先看到正在进行或即将开始的场次，再进入活动详情。地图与列表共享同一份内容和选中状态，避免同一个活动出现两个版本。

列表条目可以打开详情，也可以选择“在地图中查看”。切 tab 保留地图中心、缩放级别与筛选；关闭详情回到原视野。详情、tab 和深链接与浏览器返回键协调，避免按返回直接退出 H5。具体弹层布局、视觉与手势留到 UI 阶段确定。

## 7. 模块划分

遵循小接口承载完整行为的模块设计，不为尚未存在的变化制造额外抽象。

| 模块 | 对外接口与约束 | 内部承担的工作 |
| --- | --- | --- |
| Catalog | 查询地点、活动、餐厅和详情；所有引用来自同一版本 | 数据读取、校验、筛选、场次状态与营业状态计算 |
| ParkMap | 输入地图版本、可见地点、选中地点、当前位置；输出地点选择事件 | 投影、瓦片、镜头、标签、命中、屏幕密度与动画锚定 |
| Positioning | 用户请求定位、停止、订阅结果；显式返回失败和精度状态 | 微信/浏览器两个 adapter、授权、坐标归一、过期和异常结果处理 |
| AppShell | tab、详情与深链接状态 | 列表与地图联动、返回行为、镜头状态保存 |

Positioning 有微信和浏览器两种真实 adapter，值得设置 seam；第一版 Catalog 只有静态数据，不提前实现多种仓储。绘制素材不参与业务状态计算。

## 8. 微信与部署

普通 HTTPS 网页可以在微信中打开。接入微信 JS-SDK 则要另外确认公众号类型、认证状态、账号实际开放的接口以及 JS 接口安全域名。此处的域名备案与账号条件以当前官方文档和实际后台为准，详见平台资料核查。

签名后端保存 AppSecret，缓存 access_token 与 jsapi_ticket，根据网页当前实际 URL 签名。签名不包含 # 后的部分，其他 URL 部分按官方规则保留；iOS/Android、分享进入与前端路由变化需要实机验证。后端限制可签名的域名，返回前端需要的 appId、timestamp、nonceStr、signature；凭据不能放在 VITE_ 环境变量中。

第一版不要求微信登录。浏览器内定位需要安全上下文；localhost 可用于桌面开发，手机通过局域网 HTTP 地址测试不等同于线上 HTTPS。微信能力最终必须用真实配置域名验收。

静态素材使用带版本的路径和长期缓存；地图 manifest 与内容采用可更新策略，读取时校验版本兼容。第一版不承诺离线可用，断网时应区分已有缓存内容和实时营业/场次状态。服务端签名失败也不能阻止用户浏览静态内容。

## 9. 实施顺序与验收

1. 确认当前园区范围、底稿来源和坐标体系；建立候选设施表，区分已核验与待核验。
2. 用真实地理数据做小区域技术样片：桥、河、建筑、一个活动 pin 和位置显示；同时测 2.5D 风格与缩放表现。
3. 讨论完整 UI 与美术规范，再制作全园地图及动画资产。
4. 完成地图、餐厅、活动三个视图与统一详情；接入真实内容，处理空列表、取消场次和未知营业信息。
5. 接微信签名后端和定位；用 iOS/Android 微信真机实地验收。

必要检查包括：独立地理检查点误差；WGS84/GCJ-02 混用防护；定位拒绝/过期/园外；日期与场次状态；地图与列表联动；详情返回；低端机拖动缩放；后台停止动画；减少动态效果设置。测试围绕这些实际行为安排；第一版已有日期/镜头单元测试与桌面/手机尺寸浏览器测试，范围详见实现记录。

## 10. 后续需要补齐的输入

- 当前真实园区地图或 GIS/CAD/可核验底稿；如果暂时只有参考图，先补资料，不能以美术样图代替定位验收。
- 可用的公众号与域名情况，后续配置时再提供，不在前端存密钥。
- 地点、活动场次、餐厅和营业信息；没有数据时可用明确标注的演示内容做 UI，但不伪造营业事实。
- 喜欢的古风游戏参考或已有模型、贴图；用于统一建筑、配色与动画方向。
